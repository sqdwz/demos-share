02

原理可以略过，但“为什么要转”一定要知道

记住一个结论：不同地图体系的坐标不能直接混用。

同一地点，为什么坐标对不上？

WGS84
GCJ-02 火星坐标
GCJ-02
116.397499, 39.908722
WGS84
116.391255, 39.907318

为什么这一步不能省？

高德返回的是 GCJ-02（火星坐标）。GPS、很多国际数据和其他成果可能使用 WGS84。如果把高德返回值直接当成 WGS84 使用，点位可能整体“飘”出去几十到几百米。

分享时只讲到这里就够：不是为了讲坐标转换公式，而是让使用者知道——工具为什么同时保留两套坐标，以及什么时候应该用哪一套。
03

成品工具：四步把地址变成点

浏览器打开即可，操作逻辑尽量做成“看得懂、点得动、出错能查”。

STEP 01

导入地址表

Excel / CSV 等表格数据，识别地址、城市或区县字段。

STEP 02

调用高德 API

将文本地址批量解析为 GCJ-02 经纬度。

STEP 03

自动坐标转换

同步生成 WGS84，避免后续重复处理或混用。

STEP 04

复核与分类导出

正常、复核、失败分别处理，也可一次导出全部结果。

异常不中断

某一条地址失败，不让整批任务一起停；保留状态和失败原因，后面再处理。

问题地址可“复查”

对添加市县前缀后反而匹配失败的数据，可换一种查询方式重新尝试，避免死磕单一规则。

结果可视化核查

把坐标先放到图形预览里看分布，特别关注异常点、同址点和完全重叠点。

04

重点：AI Agent 到底参与了什么？

它不是“按一下就自动变成软件”，而是把明确的业务规则持续转成可运行的工具。

给 Agent 的需求，不要只说“做个地址转坐标工具”示例
做一个本地网页工具，用于前期调查地址批量转坐标。

核心要求：
1. 支持导入 Excel / CSV，并选择地址字段；
2. 调用高德地理编码 API 批量解析地址；
3. 同时保存 GCJ-02 与 WGS84 两套坐标；
4. 单条失败不能中断整批任务，要记录失败原因；
5. 对问题数据提供“复查”方式；
6. 做一个可缩放的图形预览，辅助发现异常点和重叠点；
7. 正常、复核、失败、全部结果可单独导出；
8. 界面尽量摊开，不做复杂流式工作区，普通人打开就会用。

请先梳理功能和数据流程，再开始实现；每完成一项说明测试办法和已知限制。
1
需求拆解先把“我要什么结果”拆成输入、处理、输出、异常和界面，而不是直接让 AI 猜。
2
接口与逻辑实现让 Agent 查文档、写请求、组织批处理，并把 GCJ-02 / WGS84 的转换封装进工具。
3
用真实数据找问题把查询不到、地址模糊、行政区前缀干扰、重复坐标等实际问题逐个喂回去修。
4
不断改成交付形态功能跑通只是第一步；后面还要调整 UI、交互、提示、导出和错误信息，直到“别人也能用”。
关键经验：Agent 擅长把规则写进工具，但它不知道你的工作口径。业务判断、结果验收和“这个工具到底能不能信”，仍然必须由使用者负责。
05

高德地图 API：使用前唯一需要准备的东西

工具可以写出来，但地址解析能力来自高德 Web 服务，所以每个使用者都应该配置自己的 Key。

注册并进入高德开放平台

打开 lbs.amap.com，完成注册登录及平台要求的认证。

创建应用

进入控制台的应用管理，创建一个用于本工具的应用。

添加 Key

平台选择 Web 服务，开通与“地理/逆地理编码”相关的服务权限。

回到本地工具粘贴 Key

Key 只作为接口调用凭证使用；公开分享工具时，不要把自己的 Key 写死在网页里。

安全提醒：“本地网页”不等于 Key 绝对隐藏。浏览器发出的网络请求仍可能被查看，因此分享工具时应让使用者自行填写 Key，并以高德控制台的安全配置和配额规则为准。
06

划重点：会用工具，更要知道它的能力和缺陷

AI 帮你做出工具之后，最重要的不是“能跑”，而是知道哪些结果能直接用、哪些必须复核。

维度
结论
工具上限
支持批量处理，但实际规模受浏览器内存、网络稳定性和接口配额共同影响；大批量数据应分批验证。
真正瓶颈
高德 API 调用配额。参考材料中给出的示例为个人 5000 次/日、企业 300 万次/日；实际以高德控制台当前规则为准。
坐标系
高德原生返回 GCJ-02，工具同步换算 WGS84，两套坐标一起保留，后续按底图或成果体系选择。
精度理解
这是“地址匹配坐标”，不是 RTK 实测坐标。地址写得越模糊，结果越需要人工确认，不能把它当测绘级成果。
异常风险
同名地点、行政区前缀、模糊地址、POI 匹配都可能造成错误；多个地址返回完全相同坐标时尤其要复核。
稳定性
应具备逐条容错、状态记录、可调请求间隔和复查机制，避免一条错误拖垮整批任务。
数据与 Key
敏感地址不应随意提交给第三方服务；Key 不应固化在公开网页中。使用前要了解接口条款、数据要求和使用边界。
先说清楚需求

AI 不怕需求复杂，怕的是需求模糊。越能把业务口径讲清楚，产出的工具越接近可用。

先跑通，再迭代

核心功能先工作，然后再补异常、预览、交互和导出，避免一开始把界面做得很漂亮但逻辑没跑通。

让 AI 解释它写的东西

关键逻辑、依赖、限制、错误处理都要让 Agent 说明白；做工具的人至少要知道哪里可能出问题。

真实数据才是测试

测试样例很乖，现场数据不乖。真正的缺陷往往是在真实地址、真实格式和真实错误中暴露出来。

写在最后

AI 的价值，不只是“帮我写一段代码”

地址转坐标这件事，单看并不复杂，但 批量、稳定、坐标系正确、异常可复核 这些要求叠在一起，就会变成一项反复消耗精力的工作。

这次真正有意思的地方，是把一个具体工作痛点交给 AI Agent 拆解、实现、测试和迭代，最后变成一个打开浏览器就能使用的小工具。

希望 AI 帮我们省下重复劳动——把精力留给真正需要判断、核查和决策的事，而不是一条条查坐标。

工具只是结果，真正可复用的是这套方法：发现重复工作 → 明确业务规则 → 交给 Agent 实现 → 用真实数据验证 → 继续迭代。 下一次遇到类似的小痛点，就不一定要继续忍着手工做。
