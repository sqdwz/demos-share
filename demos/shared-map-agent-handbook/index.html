01 /

你每天只需要记住这三步

开始前

选一个明确的目标

“修复删除图层后列表不刷新”比“全面完善地图”更容易限定范围。写出你期待看到的结果和必须保持的行为。

进行中

让一个对话负责到底

补充截图、纠正效果、修复本次回归，继续原对话。多个任务需要同时改代码时，使用独立工作树，并安排逐个整合。

结束时

收下变更与验证证据

要求列出修改文件、验证结果、未完成项、提交与部署状态。确认成果有可恢复记录，再整理或归档对话。

以下是整理建议，依据截图标题举例；没有读取这些对话全文，也没有替你移动、重命名或归档。

04 /

怎样降低“改这里，坏那里”的风险

不能靠一句“不要影响其他部分”保证零回归。要把它变成可检查的四件事：允许改哪里、必须保持什么、会影响哪些调用方、用什么证据验收。

① 限定功能与文件

写清本次目标和排除项。让 Agent 定位最小文件集合，解释每个文件为何需要改。缺陷确实跨前后端时，应覆盖完整链路；避免顺手重构、依赖升级或全局格式化。

② 检查共用入口

地图功能可能汇合到 MapView.vue；共享接口、权限、全局样式、数据库结构的变化可能影响更多页面。即使两项任务修改不同文件，也可能存在行为依赖。

③ 先隔离，再整合

同一本地目录内，建议只运行一个写代码的对话；其他对话只读。并行开发使用独立工作树。工作树隔离源码目录，但测试端口、外部数据库、业务目录和发布目标仍要分别配置。

④ 对差异做回归

审查本任务新增差异和影响链路，测试目标场景及相邻功能。提交时只收本任务文件或片段，避免 git add . 混入其他成果。构建成功不代表所有交互正确。

你截图中的“工作树”，实际怎么用？
  1. 新建独立开发任务时，在输入框附近选择“工作树”，核对起始分支。
  2. 创建后要求 Agent 报告实际工作目录、HEAD 和未提交差异。当前官方文档说明，选择含本地修改的分支时，Codex 可把这些修改带入工作树；不要假设它是干净副本。
  3. 在该目录完成开发与验证；持久保留成果时建立任务分支（如 codex/cad-overlay-fix）并记录提交。
  4. 整合前审查当前本地修改；逐个交接或合并，再对整合结果做回归。没有文本冲突也可能存在功能冲突。

归档前保存成果、提交号与交接文件。受管理的工作树可能随归档被清理；不要把唯一成果只留在临时工作树里。具体入口以客户端为准。官方工作树说明

对话太多，要不要全部删掉重来？
不用。先找出仍在执行、待验收和待上线的任务；其余确认成果已保存后归档。旧对话能帮助回查原因，但新任务通过简短交接文件启动即可，不需要复制全部聊天记录。
可以让一个 Agent 永远记住整个项目吗？
更可靠的做法是让关键事实可读取、可核实、可更新。项目持续变化，旧上下文会过时。每次任务都执行“规则 → 索引 → 相关源码 → 当前差异”的短流程，比依赖一次性全量理解更容易维护。
发现新问题，要顺便让 Agent 修吗？
与当前验收直接相关的问题在原任务中处理。无关问题先记入待办，另开目标明确的任务；扩大范围时说明原因和新增影响。这样你能清楚地审阅和回退每次变更。
